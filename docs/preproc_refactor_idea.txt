  Reorganizing by Pipeline Step: Benefits vs Drawbacks

  Benefits

  1. Pipeline stages are co-located — all download logic lives together, making
  it easy to enforce consistent patterns (retry logic, error handling, output
  format)
  2. Shared step-level utilities emerge naturally — e.g., a preprocess/utils/
  with resampling, normalization, sentinel handling that DWD and price
  preprocessing both use today but implement separately
  3. Onboarding clarity — new contributors see the pipeline flow in the
  directory tree itself
  4. Adding a new data source is guided — you know you need a module in
  download/, one in preprocess/, etc.

  Drawbacks

  1. Source-specific code gets scattered — to understand the full DWD pipeline
  today you look in weather/dwd/. After refactoring, you'd need to check
  download/dwd.py, preprocess/dwd.py, possibly augment/ and data_quality/. This
  makes source-level reasoning harder.
  2. Some modules straddle steps — dwd_fetch.py downloads zips, extracts them,
  parses CSVs, and returns DataFrames. Where does "download" end and
  "preprocess" begin? Splitting it may feel forced.
  3. The orchestration layer already provides the functional view — pipelines.py
   already organizes by step (run_price_pipeline, run_dwd_pipeline,
  run_augmentation, run_quality_report). The directory restructure duplicates
  what the code already expresses.
  4. Per-step utils/ directories risk fragmentation — with only 2-3 data
  sources, each step's utils/ would have very few files. Combined with
  preproc/utils/, that's 5-6 util locations to check.
  5. HDF5 exploration and type definitions don't fit any step cleanly —
  explore_hdf5.py, preproc_types.py, config.yaml are cross-cutting concerns.
  6. Churn vs. payoff — there are ~15 Python files with clean, non-circular
  dependencies already. The refactor touches every import path, every CLI entry
  point, and pipelines.py (which imports everything). The structural gain may
  not justify the breakage surface.

  Alternative worth considering

  A hybrid approach: keep the source-level grouping (e_price/, weather/) but
  extract truly shared preprocessing utilities (resampling, normalization,
  sentinel handling) into preproc/utils/ — which already exists. This gets the
  main benefit (DRY shared logic) without scattering source-specific code.

  the hybrid option appeal? Or a different direction entirely?
