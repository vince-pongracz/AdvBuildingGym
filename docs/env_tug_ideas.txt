This is a classic action oscillation / bang-bang control problem in RL. Here 
are the main approaches, roughly ordered from easiest to most involved:

  1. Action Smoothing Penalty (reward-based)

  Add a reward term that penalizes large changes between consecutive actions:

  penalty = -weight * |a_t - a_{t-1}|

  This is the most common fix. You'd create a new RewardFunction subclass that
  tracks the previous action and penalizes the L1 or L2 difference. Minimal code
   change, easy to tune via weight.

  2. Exponential Moving Average (EMA) Action Filter

  Instead of applying a_t directly, apply a_filtered = α * a_t + (1-α) * a_{t-1}
   in _flat_action_to_dict or within each Infrastructure.exec_action. This
  mechanically limits how fast actions can change. The agent can still request
  extreme swings, but the filter smooths them out. Downside: the agent doesn't
  "know" about the filter unless you also feed a_{t-1} into observations.

  3. Action Rate Limiting (clamp the delta)

  Clip |a_t - a_{t-1}| to a maximum Δ_max per timestep. Similar to EMA but with
  a hard bound. Again, feeding a_{t-1} as an observation helps the policy learn
  within the constraint.

  6. SAC Entropy Tuning

  If using SAC, high entropy encourages exploration of extreme actions. Lowering
   initial_alpha or setting a lower target_entropy can reduce this. For PPO,
  increasing the KL penalty or reducing the clip ratio has a similar calming
  effect.

  Does the agent actually use prev_* in practice?

  Having a_{t-1} in the observation is necessary but not sufficient. Here's why:

  With PPO: The policy network sees [..., prev_HP_action, prev_battery_action, 
  ...] as input features. But since no reward signal correlates with |a_t - 
  a_{t-1}|, there is no gradient signal pushing the network weights to connect
  the prev_* inputs to the output in a smoothness-promoting way. The network can
   learn to use them (e.g., if staying close to the previous action happens to
  correlate with higher reward through some indirect mechanism), but it has no
  direct reason to. In practice, neural networks tend to ignore input features
  that don't contribute to the loss.

  With SAC: Same reasoning, plus the entropy bonus actively encourages diverse
  action sampling — working against action consistency. SAC's objective is max 
  E[Σ r_t + α·H(π)]. The entropy term rewards stochasticity, which is the
  opposite of smoothness.

  So the statement holds: the policy can see a_{t-1} but has zero incentive to 
  stay close to it.

  ---
  On the Agent-Environment Mismatch (EMA / post-hoc clipping)

  The core issue with approaches like EMA or post-hoc delta clipping:

  Agent outputs: a_t = 0.8
  Filter applies: a_executed = 0.3 * 0.8 + 0.7 * (-0.5) = -0.11
  Environment transitions based on: -0.11
  Agent's Q-function learns: Q(s, 0.8) → r(from -0.11)   ← WRONG mapping

  For SAC: The replay buffer stores (s_t, a_t=0.8, r_t, s_{t+1}) but r_t and
  s_{t+1} resulted from a_executed=-0.11. The critic learns a corrupted
  Q-function. The actor then optimizes against this corrupted critic.

  For PPO: The log-probability log π(a_t|s_t) is computed for a_t=0.8, but the
  advantage estimate is based on returns from executing -0.11. The importance
  sampling ratio in the clipped surrogate is correct for the intended action,
  not the executed action. This corrupts the policy gradient.

  How to overcome it — two principled approaches:

  Option A: Make the filter part of the MDP (delta-action formulation)

  Redefine the action space so the agent outputs deltas:
  # Agent outputs delta ∈ [-Δ_max, +Δ_max]
  a_executed_t = a_{t-1} + delta_t

  Now the agent knows it controls the change. a_{t-1} is in the observation
  (already the case), the action semantics are explicit, and there is no 
  mismatch — what the agent outputs is what gets stored in the replay buffer and
   what the environment executes. Both PPO and SAC work correctly.

  The downside (as discussed) is that this changes action semantics and is
  invasive to implement, especially for the HP mode dimension.

  Option B: Keep absolute actions, add smoothness to the reward

  This is the simpler path. The MDP is well-defined — the agent outputs absolute
   actions, the environment executes exactly those actions, and the reward
  includes a penalty for large changes. No mismatch. Both PPO and SAC see the
  true action-to-outcome mapping.

  The prev_* observations are already there, so the agent has the information.
  The missing piece is purely the reward term.

  ---
  Bottom line: The mismatch problem only exists if you apply a filter outside
  the agent's knowledge. The two clean solutions are:
  1. Reward penalty (easiest for your setup — no mismatch, just a new
  RewardFunction)
  2. Delta-action formulation (more principled but invasive — changes action
  space semantics)

  Both avoid the mismatch entirely. EMA/post-hoc clipping should only be used at
   deployment time on a trained policy, never during training.
